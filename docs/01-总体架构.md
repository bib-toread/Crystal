# 01 · 总体架构

> 本篇建立全局观：系统由哪些部分组成、它们如何分工、一次玩家操作如何端到端流过整个系统。细节在后续各篇展开。

## 1. 一句话定位

Crystal 是一套纯托管 C#/.NET 8 的《热血传奇2》服务端+客户端引擎，**仅 Windows**。三个核心可执行/库通过一个共享协议层通信：

```
┌─────────────────┐   长度前缀二进制封包(TCP)   ┌─────────────────────┐
│   Client.exe    │ ◄────────────────────────► │     Server.exe      │
│ WinForms+DX9    │      Shared(协议+数据契约)   │ WinForms 管理界面     │
│ 渲染/输入/表现   │                            │  + 权威世界模拟        │
└─────────────────┘                            └─────────────────────┘
        │                                                │
   .Lib 图档/地图/音频                          Server.MirDB / Server.MirADB
   (社区分发,不在仓库)                          + Envir/ 文本数据树 (平铺文件)
```

- **客户端**只负责「表现」：渲染、输入、把操作发给服务端、把服务端下发的状态画出来。它不做权威判定。
- **服务端**是唯一权威：世界里发生的一切（移动是否合法、伤害多少、掉落什么）都由服务端裁决，再广播结果。
- **Shared** 是两者之间的契约：封包定义、枚举、共享数据类型。客户端和服务端各自引用它，保证二进制读写一致。

## 2. 解决方案与项目结构

解决方案 `Legend of Mir.sln` 里与运行直接相关的是三个项目，外加一组工具：

| 项目（目录） | 目标框架 | 产物 | 职责 |
|---|---|---|---|
| **Shared** (`Shared/`) | net8.0 | 类库 | 协议层 + 数据契约。被客户端和服务端同时引用 |
| **Server.Library** (`Server/`) | net8.0 | 类库 | 游戏引擎：世界模拟、实体、战斗、持久化、网络、NPC 脚本。命名空间 `Server.*` |
| **Server** (`Server.MirForms/`) | net8.0-windows | `Server.exe` | WinForms 管理界面 + **服务端入口**，引用 Server.Library |
| **Client** (`Client/`) | net8.0-windows | `Client.exe` | WinForms + SlimDX(DirectX9) 游戏客户端 |
| AutoPatcherAdmin / LibraryEditor / LibraryViewer / CustomFormControl / PatcherWebSite | — | 工具 | 补丁构建、`.Lib` 图档编辑/查看、共享控件、补丁网站 |

> **命名陷阱**：引擎库在 `Server/` 目录（`Server.Library.csproj`），可运行的服务端 exe 在 `Server.MirForms/` 目录（`Server.csproj`）。下文说「服务端引擎代码」指 `Server/`，说「服务端管理程序/编辑器」指 `Server.MirForms/`。

## 3. 三个进程入口

- **服务端入口**：`Server.MirForms/Program.cs:12`。`Main()` 第一件事是 `Packet.IsServer = true`（决定封包反序列化方向），然后 `Settings.Load()` 读 `Configs/Setup.ini`，启动 WinForms 管理窗体 `SMain`。管理员在 `SMain` 里点「启动服务器」才真正 `Envir.Start()` 拉起世界（详见 [03](03-服务端架构.md)）。
- **客户端入口**：`Client/Program.cs:18`。设 `Packet.IsServer = false`，`Settings.Load()`，按需先跑自动补丁器 `AMain`，再启动渲染窗体 `CMain`。`DEBUG` 编译会强制 `Settings.UseTestConfig = true`，加载独立测试配置便于连本地服。
- **编辑实例**：服务端进程里其实有**两个** `Envir` 实例 —— `Envir.Main`（运行中的权威世界）和 `Envir.Edit`（管理界面里各种编辑器读写的对象）。两者通过二进制库文件同步：编辑器改 `Envir.Edit` 并 `SaveDB` 落盘，运行世界 `Envir.Main` 在启动时 `LoadDB` 读入。这点在内容开发时很关键（见 [05](05-内容开发总览.md)）。

## 4. 端到端数据流：玩家走一步

把所有部分串起来最直观的方式，是跟踪一次「玩家按方向键移动」从客户端到服务端再回到所有人屏幕的全过程：

```
① 客户端：玩家按键 → GameScene 生成 C.Walk{Direction} → Network.Enqueue
② 网络：封包序列化成 [长度][id][方向] 一帧,异步 TCP 发出
③ 服务端 IO 线程:收字节 → Packet.ReceivePacket 切帧 → 入 _receiveList 队列
④ 服务端游戏线程:WorkLoop 每 tick 调 MirConnection.Process()
     → 出队 → ProcessPacket 命中 case Walk → Player.Walk(方向)
⑤ 权威裁决:HumanObject.Walk 校验目标格能否走(阻挡/门/定身)
     - 不合法 → 回 S.UserLocation 把客户端拉回原位(纠偏)
     - 合法 → 更新服务端坐标,移动在地图格子中的登记
⑥ 广播:Broadcast(S.ObjectWalk{ObjectID,方向,坐标})
     → 发给视野(Globals.DataRange)内所有其他玩家的连接队列
⑦ 服务端游戏线程 tick 末尾:把各连接 _sendList 里积压封包
     合并成一块,一次 BeginSend 异步发出
⑧ 各客户端 IO 线程收 → 入 _receiveList
⑨ 各客户端游戏线程:Network.Process → GameScene.ProcessPacket
     命中 case ObjectWalk → 找到对应 MapObject → 把"行走"动作入其 ActionFeed 队列
⑩ 客户端渲染循环:该对象 Process() 按帧推进动画 + 像素插值,
     Draw() 用其装备图档画出平滑移动 → 屏幕上"别人走了一步"
```

这条链路里出现的每个角色，后面都有专篇：封包格式与收发（[02](02-通信协议.md)）、服务端裁决与广播（[03](03-服务端架构.md)）、客户端动画与渲染（[04](04-客户端架构.md)）。记住三个要点：

1. **客户端发起的是「请求」，不是「事实」**。坐标的事实由服务端 `Walk` 裁决，必要时用 `S.UserLocation` 纠偏——这是反作弊的基础。
2. **「发给自己」和「广播给别人」是不同封包**。给自己的是无前缀封包（`S.UserLocation`、`S.HealthChanged`），广播给别人看的是 `Object*` 封包（`S.ObjectWalk`、`S.ObjectAttack`），后者带 `ObjectID` 标明是谁。
3. **一切以 `Time` 为节拍**。服务端 `Envir.Time` 和客户端 `CMain.Time` 都是各自 `Stopwatch` 的毫秒数，所有冷却、动画、定时都基于它。

## 5. 服务端世界模型（速览）

- 单例 **`Envir.Main`** 持有整个世界：所有数据模板列表（`ItemInfoList`/`MonsterInfoList`/`MapInfoList`…）、运行期集合（`Players`/`MapList`/`Connections`）、全局发号器与计时器。
- 一条**单线程权威游戏循环** `WorkLoop()` 推进一切：每毫秒 tick 处理连接，遍历全局对象链表 `Objects` 以约 20ms 时间片调用 `MapObject.Process()`，处理地图，按计时器存盘。
- **可选多线程**只用于「非宠物怪物」的 AI 处理（`Settings.Multithreaded`），玩家/英雄/宠物/NPC 始终留在主线程。
- **实体层级**：`MapObject`（抽象）→ `HumanObject` → `PlayerObject`/`HeroObject`；`MapObject` → `MonsterObject` → 各怪物子类。
- **持久化是平铺文件**：二进制 `Server.MirDB`（世界数据）、`Server.MirADB`（账号），加 `Envir/` 下的文本数据树（NPC 脚本、掉落、配方、任务…）。

详见 [03-服务端架构](03-服务端架构.md)。

## 6. 客户端运行模型（速览）

- 渲染窗体 `CMain : RenderForm`，游戏循环由 `Application.Idle` 驱动（不是固定定时器）：空闲时持续 `UpdateEnviroment()`（逻辑：收网络、更新场景）+ 受限频的 `RenderEnvironment()`（DirectX9 渲染一帧）。
- UI 是**场景/控件树**：全局唯一 `MirScene.ActiveScene`（`LoginScene`/`SelectScene`/`GameScene`）是树根，挂着 `MirControl` 派生的控件和对话框。
- 图形走 **DirectX9**（SlimDX 封装），美术资源是 `.Lib` 图档包，由 `MLibrary` 按整数 index 懒加载贴图。
- 网络封包由 `Network.Process` 分发给**当前场景**的 `ProcessPacket`，所以场景切换后封包自动由新场景处理。

详见 [04-客户端架构](04-客户端架构.md)。

## 7. 贯穿全局的设计原则

理解这几条，读任何子系统都不会迷路：

1. **服务端权威，客户端表现**。客户端永远在「请求 + 显示」，服务端永远在「裁决 + 广播」。
2. **模板 vs 实例**。`ItemInfo` 是「物品的定义」（全服一份，存二进制库），`UserItem` 是「玩家身上这一件」（带耐久/强化，挂在角色存档）。怪物同理：`MonsterInfo` 是模板，`MonsterObject` 是运行期个体。数据靠 `Index` 关联，加载后绑定指针。
3. **数据驱动 + 代码扩展**。绝大多数内容（物品/怪物属性/掉落/NPC 对白）是**数据**，改数据不改代码；只有「新行为」（怪物 AI、技能效果、脚本命令）才需要改代码。第二册会反复用到这条边界。
4. **协议是契约，改动要端到端**。封包的枚举、类定义、注册表在 `Shared/` 里有唯一来源；新增/修改封包必须同步客户端和服务端两侧，漏一处会被静默丢弃（见 [02](02-通信协议.md)）。
5. **`Time` 是一切的节拍器**。不要用真实墙钟做游戏内计时，用 `Envir.Time`/`CMain.Time`。
